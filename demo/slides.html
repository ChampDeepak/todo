Modules 1 & 2 · Application and testing

A small app, built to be operated

Three tiers, eight endpoints

  • FrontendReact 18 + Vite SPA, served by Nginx from a multi-stage build.
  • BackendFastAPI with SQLAlchemy; GET/POST/PUT/DELETE /api/tasks, plus /stats and /{id}.
  • DatabasePostgreSQL 16, schema managed by Alembic migrations.
  • Health & readiness/health is liveness; /health/ready checks the database.
  • Metrics/metrics exposed via prometheus-fastapi-instrumentator.

Tests as the first gate

32tests passing
5test modules
0.4sfull run
  • Isolated per testEach test gets its own database, so order never changes the result.
  • Coverage across the APICRUD, filters, listing, validation and health — not just the happy path.
  • Lint in the same gateRuff runs beside pytest; style failures stop the build too.

Modules 3 & 4 · Version control and containers

Reproducible from a clone

Git discipline

  • 29 commits, each a real changeMessages describe intent, not "update" or "fix".
  • Secrets never committed.gitignore excludes .env, state files and kubeconfigs.
  • Credentials-free exampleterraform.tfvars.example ships settings without keys.

Images built small and unprivileged

  • Multi-stage frontendnode:22-alpine builds; nginx:1.29-alpine serves. Build tools never ship.
  • Slim backendpython:3.12-slim with pinned, lock-resolved dependencies.
  • Non-root at runtimeBoth images drop to an unprivileged user before the process starts.

One command locally

  • docker compose up --buildFrontend, backend and Postgres, wired together.
  • Health-gated startupThe API waits for the database to report healthy rather than racing it.
  • Migrations on bootThe entrypoint applies Alembic migrations before serving.

Four jobs, explicit dependencies

  • Lint and testRuns against a real PostgreSQL service container.
  • Build frontendRuns in parallel; independent of the tests.
  • Build, scan and push ×2A matrix over backend and frontend. Reached only if the gates pass.
  • Scan before push, not afterThe image is built locally, scanned, and published only on a clean result.

Tagged by commit, never latest

  • One identifier end to endCommit, CI run, image and running pod all carry the same SHA.
  • Exampleghcr.io/champdeepak/todo-frontend:sha-28d10a4…
  • Rollback becomes trivialA previous version always exists to return to — with latest it does not.
  • ProvenanceAny running container can be traced back to the exact source that produced it.

Module 6 · DevSecOps

The scan caught something real

Trivy runs on every build with severity: HIGH,CRITICAL and exit-code: 1. ignore-unfixed is on, so the gate blocks only on findings someone can actually act on — a scanner that cries wolf gets switched off.

What it found

  • 43 findings in the frontend image41 HIGH and 2 CRITICAL, nearly all in OpenSSL.
  • CVE-2026-31789 — CRITICALHeap buffer overflow in OpenSSL, fixed upstream in 3.3.7.
  • Root cause: an aged base imagenginx:1.27-alpine shipped Alpine 3.21 with OpenSSL 3.3.3.
  • The push was blockedThe vulnerable image never reached the registry.

What changed

  • Base image moved forwardnginx:1.29-alpine — Alpine 3.23, OpenSSL 3.5.6.
  • Scan now clean0 vulnerabilities across 71 OS packages; secret scanning passes too.
  • Visible in historyCommit d1fb04c exists for no other reason than this fix.
  • The lessonThe flaw was not in code we wrote. It was in a dependency that aged — which is why the scan runs on every build, not once at review.

  • No credentials in the repoAuth comes from the AWS CLI profile; state and tfvars are gitignored.
  • Cost disciplineEKS bills $0.10/hour whether or not a pod runs, so teardown is part of the workflow.

Taskr — DevOps Capstone08
What actually went wrong

Three failures worth keeping

A silent cloud quota

  • SymptomThe node group sat for 25 minutes with zero instances and no error on the resource itself.
  • CauseA Free Tier account refuses any instance type not on its list. t3.medium is not.
  • LessonThe real reason was only in the Auto Scaling group's activity history. Read the layer that actually launches things.

An interrupted destroy

  • SymptomA rebuilt node group failed: instances ran, but never joined the cluster.
  • CauseA cancelled terraform destroy had already deleted the route table in parallel, leaving subnets with no route out.
  • LessonInterrupting a destroy is not an undo. What survives depends on the graph, not on intent.

A stale base image

  • SymptomCI went red on an image whose application code had not changed.
  • CauseA critical OpenSSL CVE disclosed against the pinned Alpine base.
  • LessonDependencies rot without being touched. Scanning every build is what makes that visible.
Taskr — DevOps Capstone09
Module 10 · Review

What this demonstrates

Every gate is automatic

  • Tests, lint and a vulnerability scan all run before an artifact exists. Nothing reaches the registry on a human's say-so.

Every artifact is traceable

  • The commit, the CI run, the image tag and the running pod share one identifier, which is what makes a rollback a single command.

The environment is disposable

  • Fifteen resources destroyed, then fifteen planned to add from the same configuration. Nothing was clicked, and nothing was left billing.

Known shortcuts, stated plainly

  • Postgres runs in-cluster rather than RDS, migrations run in the entrypoint rather than a Job, subnets are public to avoid NAT cost, and state is local. Each is a deliberate trade, documented in the README.
